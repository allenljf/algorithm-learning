# Authentication Registration Recovery Plan

## Architecture

`ApiExceptionHandler` is the boundary where unhandled API exceptions become a
safe `ProblemDetail`. It will log the exception with the request ID already
generated by `RequestIdFilter`, then retain the existing safe response. A
diagnostic Cloud Run release permits a synthetic, non-user registration to
identify the failing component. The smallest correction is then made at that
component, proven with a regression test, and released through the existing
same-project Firebase rewrite.

## Files and responsibilities

- `services/api/src/main/java/.../app/web/ApiExceptionHandler.java`: safe,
  correlated server-side unexpected-error logging.
- `services/api/src/test/java/...`: regression coverage for the actual failing
  registration component once production evidence identifies it.
- `specs/auth-registration-recovery/*`, `agent-workflow/*`: task contract,
  diagnostic evidence, release evidence, and completion state.

## Verification strategy

The task runs the focused API test suite after each code correction, packages
the API image, deploys it to the existing `asia-east1` service without changing
its non-secret or secret configuration, confirms public readiness, and sends a
single generated registration request through the public Firebase origin.

## Rollout and recovery

The first diagnostic image changes only internal logging. If it exposes a
runtime configuration defect, the final image corrects that defect and is
redeployed. If the correction cannot be verified after three bounded rounds,
the service remains on the last ready revision and the task enters the existing
recovery loop with redacted evidence.

Cloud Run runs the existing service on `linux/amd64`. Local Docker builds must
therefore specify that platform; an ARM-only image fails before Java starts and
must never receive production traffic.
